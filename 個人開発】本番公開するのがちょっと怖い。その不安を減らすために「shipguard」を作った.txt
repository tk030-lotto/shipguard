# 【個人開発】本番公開するのがちょっと怖い。その不安を減らすために「shipguard」を作った

Webアプリを作っていて、ある程度完成してくると、別の不安が出てきます。

「これ、本当にこのまま公開して大丈夫かな？」

アプリ自体は動いている。

画面も表示される。

必要な機能も一通り動く。

でも、本番公開の直前になると、コードを書いているときとは違う種類の心配が出てきます。

`.env` に入れた秘密情報は大丈夫だろうか。

公開してはいけないキーがフロントエンドに混ざっていないだろうか。

SupabaseのRLSを設定し忘れていないだろうか。

開発中に設定したCORSが、そのまま残っていないだろうか。

こうした問題は、アプリを普通に動かしているだけでは気づきにくいものです。

そこで、**本番公開前にプロジェクトを機械的にチェックするCLIツール**を作ることにしました。

それが「shipguard」です。

---

## shipguardは何をするツールなのか

`shipguard`は、個人開発者向けの**事前ローンチ・セキュリティ＆設定監査CLI**です。

プロジェクトをローカルで走査して、

* ハードコードされた秘密鍵
* 公開用環境変数への秘密情報混入
* Supabase / PostgreSQLのRLS設定漏れ
* 過度に開放されたCORS
* `.env.example`と実際の環境変数の不整合

などをチェックします。

基本的な使い方は非常にシンプルです。

```bash
npx shipguard scan
```

これだけです。

※ GitHub Releasesから直接パッケージ（zip）をダウンロードして利用することも可能です。
* 最新リリースページ: https://github.com/tk030-lotto/shipguard/releases/latest
* 最新アセット（zip）直接ダウンロード: https://github.com/tk030-lotto/shipguard/releases/latest/download/shipguard-v0.1.0.zip

そして、このツールで最初から重視したのが、

**外部サービスに依存しない**

ということでした。

サーバーを立てない。

データベースを持たない。

監査データを外部に送らない。

アカウント登録も必要ない。

ローカル、またはCI環境だけで完結させる。

READMEでも「サーバー不要・外部費用0円・ローカル完結」を基本方針にしています。

---

# 最初は「ファイルを調べればいい」と考えていた

最初に考えた構成は、それほど複雑ではありませんでした。

プロジェクトのファイルを再帰的に取得して、危険な文字列や設定を検索する。

いわゆる静的解析です。

ところが、実際に設計してみると、単純な文字列検索では済まないことが分かってきました。

例えばシークレット検知。

StripeやOpenAIなどのAPIキーらしき文字列を見つけたら警告する。

これは比較的簡単です。

しかし、テストコードには意図的に「偽のAPIキー」を書いていることがあります。

`.env.example`にも、本物ではないプレースホルダーが入っています。

そこまで全部検出してしまったら、警告だらけになります。

そこで、

* テストファイルの除外
* プレースホルダーの除外
* 検出した秘密情報のマスキング

などを入れていきました。

セキュリティツールなのだから、**ツール自身が秘密情報を画面にそのまま表示するようでは困る**わけです。

---

# 一番難しかったのはRLSだった

今回の開発で、特に設計を考え直すことになったのがSupabase / PostgreSQLのRLSでした。

最初は、

```sql
CREATE TABLE users (...);

ALTER TABLE users ENABLE ROW LEVEL SECURITY;
```

のようなSQLを見つければいいと思っていました。

ところが、実際のマイグレーションでは、こんな構成になることがあります。

```text
001_create_users.sql
002_enable_rls.sql
003_add_columns.sql
```

テーブルを作ったファイルと、RLSを有効化したファイルが違います。

つまり、

**「1ファイルの中に両方の記述があるか」**

だけでは正しく判断できません。

ここで、単純な正規表現による判定から考え方を変えました。

プロジェクト内のマイグレーションをすべて調べ、

```text
CREATE TABLEされたテーブル
        ↓
RLSが有効化されたテーブル
        ↓
両者の差分を計算
```

という方式にしました。

これなら、別のマイグレーションで後からRLSを有効化した場合でも確認できます。

さらに、プロジェクトによってはRLSの対象外にしたいテーブルもあるので、`database.excludeTables`による除外設定も用意しました。

ここで、

**「セキュリティ監査だから、とにかく正規表現で探せばいい」**

という考え方では限界があることを実感しました。

---

# 「KEY」が付いていれば危険、ではない

環境変数のチェックでも同じ問題が出ました。

例えば、

```text
NEXT_PUBLIC_SUPABASE_ANON_KEY
```

という名前を見たとします。

`PUBLIC`

`KEY`

が入っています。

単純なルールなら、

「公開されているKEYだから危険！」

と判定してしまいそうです。

でも、これは公開を前提としたキーです。

つまり、単純に単語だけを見るのではなく、

**そのキーが何のために公開されているのか**

まで考えないといけません。

そこで、

* `ANON`
* `PUBLISHABLE`
* `PUBLIC_KEY`

などをホワイトリストとして扱い、公開前提のキーを誤検知しないようにしました。

このあたりから、`shipguard`は単純な「文字列検索ツール」ではなくなっていきました。

---

# 監査したなら、その結果も残したい

もう一つ考えたのが、監査結果の履歴です。

一度チェックして問題を修正したとしても、

「前回はどうだった？」

ということがあります。

そこで、監査結果を

```text
.shipguard/audit.log
```

に保存することにしました。

形式はNDJSONです。

1回の監査につき1レコードを追記します。

そこには、

* 実行日時
* Gitコミットハッシュ
* スキャンしたファイル数
* 違反件数
* 重要度別件数
* 合否
* 検出内容

などを記録します。

これならデータベースを用意しなくても、監査の履歴を残せます。

そして、

```bash
npx shipguard history
```

で過去の監査履歴を見ることもできます。

---

# CIにも入れられるようにした

ローカルでチェックするだけではなく、CI/CDにも入れられるようにしました。

例えばGitHub Actionsなら、

```bash
npx shipguard scan --strict
```

をデプロイ前に実行できます。

重大な違反があればExit Code 1。

問題がなければExit Code 0。

つまり、

```text
コードを変更
   ↓
GitHubへPush
   ↓
shipguard
   ↓
問題あり → デプロイ停止
問題なし → 次の処理へ
```

という流れにできます。

個人開発では「最後に自分が確認する」だけになりがちなところを、機械的なチェックとしてパイプラインに入れられるようにしました。

---

# CLIだけでは少し味気ない

ここまで作ると、今度は別のことが気になりました。

CLIとしては動く。

でも、監査結果を毎回ターミナルだけで確認するのは少し味気ない。

そこで、ローカルWeb UIを追加しました。

```bash
npx shipguard ui
```

とすると、ブラウザでダッシュボードを開けます。

ここでも、

**外部サービスは使いません。**

Node.js標準の`http`とVanilla HTML/CSS/JavaScriptを使ったローカルUIです。

監査結果だけでなく、過去の監査履歴もブラウザから確認できます。

---

# さらに「パスを入力するのも面倒」になった

Web UIを作ったら、今度は別の問題が出てきました。

「プロジェクトのパスを手入力するのは面倒では？」

そこで、OS標準のフォルダ選択ダイアログを呼び出せるようにしました。

ブラウザ上で、

**📁 フォルダ選択**

を押して対象プロジェクトを選ぶ。

これだけでスキャンできます。

単一ファイルを選択して監査することもできます。

手入力によるパスの間違いも減らせます。

---

# Windowsでは最後に別の問題が待っていた

さらに、Windowsならダブルクリックだけで起動できた方が便利です。

そこで、

```text
shipguard-ui.bat
```

というランチャーも用意しました。

ところが、ここでWindowsの`.bat`ファイル特有の問題に遭遇しました。

`cmd.exe`では、括弧の扱いや改行コード、文字コードなどに独特の注意点があります。

最終的には、

* CRLF
* Shift-JIS（CP932）
* 括弧ネストを避ける

といったWindows向けの仕様に合わせて調整しました。

Webアプリのセキュリティ監査ツールを作っていたはずなのに、最後にはWindowsのバッチファイルまで深掘りすることになりました。

個人開発をしていると、こういうことが結構あります。

---

# 途中から「ツールの構造」も重要になった

機能が増えてくると、今度はコードの構造が問題になります。

そこで、処理を一つに詰め込むのではなく、

```text
Scanner
   ↓
Rule Engine
   ↓
Config Filter
   ↓
Severity Resolver
   ↓
Reporter / Logger
```

という多層構造にしました。

ファイルを探す。

ルールで検査する。

設定による除外を適用する。

重要度を決める。

結果を表示・保存する。

それぞれの責務を分離しています。

こうしておけば、今後監査ルールを増やす場合でも、コア部分を大きく変更せずに済みます。

---

# テストも機能追加と一緒に増えていった

開発の途中では、テストも段階的に増やしました。

Phase 1では4テスト。

Phase 2では25テスト。

Phase 3では41テスト。

Web UIなどの追加後には45、46テストへと増えています。

そしてコードレビューで指摘された部分も修正し、最新の改善では**53テスト全件PASS、型チェックPASS**まで確認しました。

単純に「機能が動いたから完成」ではなく、

**機能を追加する → テストする → 問題があれば設計を見直す**

という流れで進めました。

---

# 作ってみて分かったこと

今回の開発で一番印象に残ったのは、

**セキュリティチェックは、検出することより「正しく検出すること」の方が難しい**

ということです。

秘密鍵を見つける。

これは比較的簡単です。

でも、

「これは本当に秘密情報なのか？」

「これはテスト用ではないのか？」

「これは公開していいキーではないのか？」

「別のファイルで設定済みではないのか？」

まで考え始めると、一気に難しくなります。

だから`shipguard`では、単純な正規表現だけに頼るのではなく、

**ファイル構造、設定、複数ファイルの関係、例外設定**

まで含めて判断する方向に進化していきました。

---

# そして、最初の目的に戻る

最初に考えていたのは、

> 「本番公開する前に、もう一度チェックしたい」

という非常にシンプルなものでした。

最終的な`shipguard`は、

* CLI監査
* シークレット検知
* 環境変数監査
* RLS監査
* CORS監査
* 監査履歴
* JSON / Markdown / HTMLレポート
* CI/CD対応
* ローカルWeb UI
* フォルダ・ファイル選択
* Windowsワンクリック起動

まで広がりました。

それでも、最初から最後まで変えなかったものがあります。

**外部サービスに依存しないこと。**

**ローカルで完結すること。**

そして、

**本番公開前の「ちょっと不安」を減らすこと。**

---

# おわりに

個人開発では、コードを書いている時間だけが開発ではありません。

本番公開直前になって、

「これ、大丈夫かな？」

と確認する時間もあります。

その確認を毎回自分の記憶だけに頼るのではなく、機械に任せられる部分は任せる。

そのための工具として作ったのが`shipguard`です。

もちろん、静的解析だけですべてのセキュリティ問題を発見できるわけではありません。

それでも、

**「公開前に最低限ここは確認しておきたい」**

という項目を自動でチェックできれば、ローンチ前の不安を少し減らすことはできます。

個人開発だからこそ、大きなセキュリティサービスを導入するのではなく、

**必要なチェックを、自分のPCで、自分のプロジェクトに対して実行する。**

そんな小さな工具を一つ作ってみました。

これが、今回の`shipguard`です。
